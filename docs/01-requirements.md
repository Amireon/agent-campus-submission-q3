# 需求、用户与成功标准

## 用户与目标

企业员工需要快速确认制度或产品规则：年假多少天、报销期限多久、退款政策、采购审批、信息安全要求等。真实知识库通常存在多份版本、不同适用范围和相互冲突的条款。用户的目标不是“得到一个像答案的句子”，而是：

1. 明确知道答案依据哪份文档、哪一段原文；
2. 资料冲突时知道冲突在哪里、需要向谁确认；
3. 资料不足或工具失败时得到诚实的“不知道/未完成”，而不是编造；
4. 评测者能复现每一步工具调用和结果。

## 输入与范围

用户输入 `question_id`、`question`，可选 `history`（最多 8 条 user/assistant 消息）。

合成文档库 `data/docs.json` 包含 12 份制度/FAQ，每份带 `doc_id`、`title`、`version`、`effective_date`、`status`（active/superseded/draft）、`scope`、`department`、`tags` 和若干 `sections`。

本项目交付：

- Python CLI：单问题 `ask` 与验收矩阵 `demo`；
- DeepSeek Flash 真实模型接入与显式离线 Mock；
- 三个工具：`search_docs`、`read_doc`、`finish`；
- 引用、数字、文档状态和冲突的代码级校验；
- 29 项自动测试、9 组模拟 + 9 组真实运行、Trace 与文档。

不实现：真实企业知识库/权限系统、向量检索、文件上传解析、UI、线上部署、多 Agent、实时文档同步、多轮会话存储。

## 六个必须验收点

| 验收点 | 成功标准 | 实际用例 |
| --- | --- | --- |
| 明确答案 | 只依据已读取的现行文档，给出明确结论与逐字引用 | `answer`、`version` |
| 文档冲突 | 多份现行文档数值不同且无法判断优先级时，列出双方、引用原文、请求确认，不擅自选一个 | `conflict` |
| 资料外问题 | 多轮改写检索后仍无资料，返回 `not_found` 并说明缺口，不编造 | `out_of_scope` |
| 改写后的相似问题 | 原问题无法直接命中时，模型改写成可检索的关键词并找到正确文档 | `paraphrase` |
| 上下文追问 | 结合 `history` 把“那上限是多少”改写成独立问题，找到正确文档 | `followup` |
| 工具失败 | 可重试一次；持续失败返回 `failed`，无引用、无编造；瞬时失败后恢复 | `tool_failure`、`tool_recovery` |

附加验收：`step_limit` 验证执行上限返回 `incomplete`；`version` 验证旧版文档不能作为依据；`conflict` 的 Trace 中还能看到模型因 `UNSUPPORTED_NUMBER` 被拒绝后修正答案。

## 业务规则

1. `answered` 必须至少一条引用；`needs_clarification` 至少两份不同文档和具体待确认问题；`not_found` 必须说明缺口；`failed` 不得携带引用。
2. 引用必须来自本轮 `read_doc` 读取过的 `active` 文档，且为章节原文的逐字片段（空白/标点归一化后比较）。
3. 答案中的数字必须能在引用原文、所引文档元数据或用户问题中找到；否则工具返回 `UNSUPPORTED_NUMBER`。
4. 同标题下多份 `active` 文档数值不同时，工具返回 `conflict_signals`；`finish` 拒绝“只引用其中一份且未说明适用范围”的 `answered`。
5. `superseded` 和 `draft` 只能说明其存在，不能作为答案依据。
6. 工具失败时不得假装成功，也不得自动降级到 Mock。
7. 本项目没有“发布”概念；知识问答不修改任何文档。

## 数据声明

所有文档、规则、版本号、部门与数值均为合成内容，用于工程考核，不来自真实公司，也不构成法律、财务或人事结论。D01/D02 是刻意保留的同主题冲突；D07/D08 是“旧版被替代”场景；D09 是未生效草稿；资料外问题（营收）没有对应文档。
